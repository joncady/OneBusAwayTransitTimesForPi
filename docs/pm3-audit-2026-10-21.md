# PROXmobil3 hardware and software audit

Audit date: 2026-10-21 (Pacific time). Inspected the actual device through SSH, after USB key setup. This report distinguishes direct observations, community documentation, and recommendations. The existing Node/Python implementation is not a requirement for the port.

## Assessment

The reader is a viable host for a small native arrivals display. It has a working Linux framebuffer, Ethernet, outbound HTTPS, fonts, and enough idle memory for further evaluation. A browser kiosk would require substantially more platform work than a native framebuffer app.

**Preferred candidate to evaluate:** one Rust application with a Slint software-rendered UI, direct OneBusAway requests, configuration files, and a systemd service. Keep the installed OS for the first experiment. This is a recommendation based on the inventory and an existing project for this hardware, not a measured application benchmark or a final technology decision.

Three issues affect the product requirements regardless of language:

1. The system clock is nearly five hours behind real UTC, and the OS timezone is US/Central. Arrival calculations and schedules need a trustworthy clock.
2. There is no working Linux input device. Touch-to-wake and an on-screen mode toggle are currently unproven requirements.
3. Standard Linux backlight controls are absent. Vendor PIC control commands exist, but their behavior needs a separate reversible experiment.

## Audit scope and evidence

Inspected CPU, memory, block devices, mounts, boot logs, kernel configuration, live device tree, buses, graphics, input, audio, network, firmware/modules, packages, executable/library inventories, startup scripts, service definitions, clock, effective SSH options, and exposed power interfaces. Made credential-free HTTPS requests and sampled idle CPU and small sequential storage reads.

No device files, services, network settings, clock, firmware, packages, or display state were intentionally changed. Commands did not invoke hardware control operations. Normal SSH/journal activity and filesystem reads can still produce routine OS bookkeeping. Existing vendor scripts were read, not executed. No OneBusAway key or private transit configuration was copied to the reader.

Raw observations and collection commands are saved in the ignored `pm3-audit.local/` directory, including the kernel configuration and boot device tree. These contain device and network identifiers and are not intended for Git. This Markdown report omits private IP/MAC addresses, keys, stop IDs, and home location names.

This is a remote operational audit, not board disassembly, electrical measurement, a vulnerability scan, or a full hardware stress test. Full disk/firmware backups and application benchmarks have not been performed.

## Input and Wi-Fi findings

### Touch cannot be assumed

The kernel has `CONFIG_INPUT_EVDEV=y`, but `CONFIG_INPUT_TOUCHSCREEN` is not set. Follow-up inspection confirms `CONFIG_HID_MULTITOUCH=y` and `CONFIG_USB_HID=y`: USB touch support is present, despite the absence of dedicated touchscreen drivers. No input devices or USB touch controllers enumerate. The vendor service names `/dev/input/event0`, and `gui.ini` contains `TouchPanel=true`; those configuration values do not prove a touch controller exists or works on this variant.

The supplied [RIPTA system design document](https://kevin.wallace.seattle.wa.us/pm3/ripta-system-design-document.pdf), page 9, explicitly marks both touch panel and controller as optional. It describes a product variant, so physical inspection is still needed to establish whether this unit lacks them or has a disconnected/unpowered controller. There is no demonstrated software toggle to enable touch here. Page 12 also specifies only 754 × 480 pixels visible through the enclosure; a layout should leave generous horizontal margins despite the full 800-pixel framebuffer.

Touch-to-wake, manual scrolling, a mode toggle, and an on-screen refresh control need an input investigation before promising equivalent behavior. Opening the unit to inspect its display/controller could settle hardware presence. A kernel or driver change would only help if matching hardware exists. Alternatives include automatic mode rotation, a local web settings page, or a known compatible external input device. NFC/barcode wake is a separate integration project, not a substitute established by this audit.

### Onboard Wi-Fi is likely absent, not merely unconfigured

The live device tree names `ti,wl1837` under an enabled SDIO host. Driver modules and TI firmware are present. However, the SDIO bus contains no devices, mmc1 is powered off, no wireless PHY exists, and the WLAN regulator GPIO is low.

More significantly, the community board overview identifies the WiLink position as an **unpopulated footprint**. This makes physical absence a stronger explanation than the earlier assumption that a device-tree entry proved installed hardware. It is still an inference for this specific unopened unit. [Board overview](https://wiki.pm3.dev/main_board_overview)

Use Ethernet for the first version. For wireless placement, an external Wi-Fi-to-Ethernet bridge could avoid device-driver changes; a USB Wi-Fi adapter would need a driver supported by this exact kernel. Neither accessory has been selected or tested.

## Display power, scheduling, and clock

There is no device under `/sys/class/backlight`; `CONFIG_BACKLIGHT_PWM` is disabled. Three PWM controllers exist but are unclaimed, and their connection to the display is unproven. X11 `xset`/DPMS from the Pi app cannot be reused here.

Read-only vendor command help exposes:

```text
NxExe pic [-lcd|-bootconfig] [0|1|false|true|configbyte]
NxExe prox2 ... backlight ...
NxExe pic32 valueread / valuewrite ...
```

These are candidates for a controlled LCD/backlight experiment. No command that changes those values was run. In particular, `prox2 backlight` is described as a toggle; blindly using a toggle in a scheduled policy could invert the desired state after a crash. Prefer a confirmed idempotent control with state/readback.

Linux exposes `freeze`, `standby`, and `mem` suspend states, and rtc0 is marked wake-capable. This does not establish that suspend/resume, RTC alarm wake, Ethernet recovery, or touch wake works. Ethernet reports Wake-on-LAN disabled/unsupported (`d`). Do not rely on full shutdown followed by automatic wake yet. First implement stopping API polling and controlling the backlight while keeping Linux running.

The clock sample was `2026-10-21T20:27:27Z` while the host and HTTPS server were around `2026-10-22T01:24:42Z`: roughly **4 h 57 min slow**. The separate OS timezone is `US/Central`. No active NTP/chrony/systemd-timesyncd service or normal time-sync executable was found. The cause of the UTC offset and RTC retention is not established; changing the display timezone alone will not fix UTC.

Before live countdowns, establish time synchronization, validate UTC and Pacific scheduling, and show a clear unsynchronized/offline state. Use monotonic time for retry/refresh/idle intervals and wall time for arrivals and commute schedules.

## Boot, persistence, and reliability

Observed startup is systemd → `init-rc.service` → `/init/tools/initexec.sh startup` → ordered `/init/autorun/*` scripts. `/init` is mounted by the filesystem label `init`, which must be preserved. The root filesystem is read only; `/init` is writable. The USB drive is found by its `MP_SD` label when the normal external-card path is unavailable.

The installed `90-testmode.sh` detects the dongle EEPROM's TestMode payload, stops the stock UI, disables the PIC watchdog, and runs the extracted bootstrap. This explains why the current reader stays reachable without the stock fare app. The stock UI's framebuffer contents can remain visible even after its process stops.

There are two distinct watchdog paths:

- systemd configures the Linux hardware watchdog at a ten-second runtime interval.
- The PIC watchdog is managed by the vendor tools/startup flow. Community documentation warns that stopping the stock UI without handling this watchdog can cause a later poweroff. [NX notes](https://wiki.pm3.dev/nx), [PIC protocol](https://wiki.pm3.dev/pic32)

Do not casually disable the Linux watchdog or reuse the stock service definition: `nx.service` contains `FailureAction=poweroff`. A replacement service should restart the app on failure and preserve remote recovery access. Current `systemctl --failed` reports no failed loaded units.

The boot log includes one USB descriptor timeout followed by successful enumeration, an early Ethernet link bounce followed by a stable link, and ext4 journal recovery for the writable card. These observations do not establish defective hardware. Repeated boot tests and storage health checks remain future work. Avoid continuous writes or unbounded logs on the small cards.

Before deployment, back up both internal cards and the 16 MiB SPI flash, plus boot assets, system configuration, and the working USB bootstrap. A live image of writable `/init` may be inconsistent; make a consistent/offline copy or define a recovery procedure. Kernel config and DTB copies collected here are evidence, not full recovery backups. Firmware on the PIC/NFC/barcode modules is outside this audit's backup scope.

The community storage documentation describes separate root/data cards and cautions that root-card access requires disassembly. A future storage or OS upgrade must preserve the boot chain and the `init` label. [Storage notes](https://wiki.pm3.dev/storage)

## Maintenance and access

Root SSH key login works. Effective sshd settings also allow password and challenge-response authentication; no root password was read or changed. A replacement deployment should preserve the working key, validate a second session, and then explicitly choose the intended authentication policy.

SSH listens through a systemd socket; DNS/LLMNR listeners are also present. No vendor app HTTP listener is currently running. The OS ships old kernel/TLS/SSH packages and has no established update feed. The boot log says systemd's BPF service IP firewall feature is unavailable; this does not by itself prove whether any other firewall exists. This audit did not perform a CVE assessment or hardening changes. Keep external exposure out of the initial deployment plan.

Store the API key and location configuration in private files under `/init` with restrictive permissions. Use a maintained TLS client/build for the chosen app and validate certificates. Any local settings endpoint should expose only what its clients need and should not return secrets. Keep raw backups and hardware dumps outside version control.

## Implementation options after profiling

| Option | Fit for this reader | Tradeoff / unresolved proof |
| --- | --- | --- |
| **Rust + Slint software UI** | Strongest candidate: compiled app, declarative layout, direct framebuffer, network/config/scheduling in one process | Requires ARM cross-build and a carefully chosen framebuffer backend. Actual memory, rendering, font support and TLS compatibility must be measured. |
| Go + a framebuffer renderer | Plausible small app with HTTP/JSON/config in one binary | More custom UI/font/layout work unless a suitable toolkit is chosen; rendering and input integration still need proof. |
| C/C++ + LVGL or a small renderer | Plausible resource-conscious approach with explicit hardware control | More manual integration for HTTP/TLS/JSON/configuration and memory management; build a compatible sysroot/toolchain. |
| C++ + installed Qt 4 Embedded | Reuses the existing vendor display toolkit | Inherits a legacy toolkit and exact ABI/toolchain dependencies; unattractive as the long-term foundation. |
| Python or Node plus browser kiosk | Possible research direction, not excluded purely by RAM | No runtime, browser, X11 or Wayland is installed; runtime installation alone does not provide a UI. Largest departure from the working platform. |
| Replace the OS | Potential future maintenance improvement | Board-specific kernel, device tree, PIC, GPU and boot work; ordinary Raspberry Pi images do not target this hardware. Separate project after backups and a recovery path. |

The PM3 community lists an existing [OneBusAway arrival board](https://github.com/haylinmoore/board) using Rust, Slint, and framebuffer rendering. Its documented target explicitly supports glibc 2.28. This is relevant evidence that the architecture is practical on this hardware family, not independent validation on this device. Review its approach before deciding whether to reuse code or build a separate implementation.

Current [Slint LinuxKMS documentation](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backend_linuxkms/) also describes legacy `/dev/fbX` software rendering. Do not assume every Slint backend/version will work on this old kernel: select versions/features deliberately, avoid unneeded GPU/input dependencies, and validate an actual executable. A static or glibc-2.28-compatible build avoids depending on a newer host libc.

## Proposed checkpoints

1. **Review this audit and resolve physical assumptions.** Decide whether Ethernet is acceptable and whether opening the case to identify touch/Wi-Fi hardware is worthwhile. No language choice fixes absent hardware.
2. **Capture recovery backups.** Preserve internal cards, SPI boot flash, original settings and the working USB key-access path before deployment changes.
3. **Run a disposable rendering experiment.** Cross-build a minimal Rust/Slint framebuffer screen, run temporarily from RAM, and measure startup, RSS, CPU, text legibility and redraw behavior. Include ASCII and the actual transit labels needed. Keep a documented way to stop it and recover SSH.
4. **Validate time, power and input independently.** Establish time synchronization; test LCD off/on with recovery; determine whether an input method can wake/switch modes. Measure real power only with an external meter if required.
5. **Choose the stack using those results.** If the native experiment succeeds, use one process for arrivals, scheduling and display. Preserve private JSON configuration and API-key handling, but replace the Pi-specific browser/DPMS/deployment pieces.
6. **Implement and validate the complete display.** Check live train/bus modes, stale/offline/error states, configurable refresh, scheduled polling, wake policy, automatic startup, abrupt power recovery, network loss and updates/rollback.

A native implementation would reuse product behavior, branding/layout decisions, transit configuration concepts, and arrival normalization rules. The React components, Python SDK wrapper, browser input handling, and X11 power manager would be replaced as needed. No port or deployment was started during this audit.
